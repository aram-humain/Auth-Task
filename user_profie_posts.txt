Task 4: User Profile Management + Posts

Goal

Continue the existing Authentication and Role Management system by adding User Profile and Posts functionality.

A user should be able to have a personal profile, update their information, have a profile picture, and publish posts.

This functionality should work with the existing authentication and authorization system.


--------------------------------------------------
1. User Profile
--------------------------------------------------

Each registered user should have a profile.

The profile should contain at least:

- First Name
- Last Name
- Phone
- Location
- Date of Birth
- Bio
- Profile Picture

The user should be able to view and update their profile information.


--------------------------------------------------
2. Profile Picture
--------------------------------------------------

The user should be able to:

- Add a profile picture
- Replace an existing profile picture
- Remove a profile picture

The profile should also work correctly when the user does not have a profile picture.


--------------------------------------------------
3. Profile Access
--------------------------------------------------

Users should be able to view other users' profiles.

A user should only be able to modify their own profile.

An Admin should be able to view all user profiles.


--------------------------------------------------
4. Create Post
--------------------------------------------------

A logged-in user should be able to create a post.

A post should contain at least:

- Title
- Content
- Created Date

The post should be associated with the user who created it.


--------------------------------------------------
5. View Posts
--------------------------------------------------

Users should be able to view their own posts and posts created by other users.

A user's profile page should display the posts published by that user.

For example:

User A Profile
→ User A Posts

User B Profile
→ User B Posts


--------------------------------------------------
6. Edit Post
--------------------------------------------------

A user should be able to edit posts they created.

After an update, the new post information should be displayed wherever the post is shown.


--------------------------------------------------
7. Delete Post
--------------------------------------------------

A user should be able to delete posts they created.

A deleted post should no longer be available during normal application usage.


--------------------------------------------------
8. Post Ownership
--------------------------------------------------

A user should not be able to edit or delete another user's post.

Posts created by other users should only be available for viewing.


--------------------------------------------------
9. Posts Feed
--------------------------------------------------

Create a common page where users can view posts published in the system.

For example:

/posts.php

For each post, display at least:

- Author
- Title
- Content
- Created Date

It should be possible to navigate from the author's name to their profile page.


--------------------------------------------------
Expected User Flow
--------------------------------------------------

Register
→ Verify Email
→ Login
→ Open Profile
→ Add / Edit Profile Information
→ Add Profile Picture
→ Create Post
→ View Post
→ Edit Post
→ View Other User Profile
→ View Other User Posts

POSTS / SOCIAL NETWORK IMPLEMENTATION HANDOFF
======================================================================

This section records the database design agreed for the pilot social
network and the work that remains. No application code has been
implemented for these social features yet.


1. AGREED ARCHITECTURE
----------------------------------------------------------------------

The application uses:

- PHP
- PDO
- MySQL 8.0
- InnoDB
- Session authentication through includes/auth.php
- Cloudinary for uploaded images
- The existing Dashboard as the feed page

There will not be a separate Feed component for now. Dashboard.php will
load the feed data and Dashboard.html.php will render it.

Visibility decision:

- Authenticated users may view posts.
- Only the post owner may edit or delete their post.
- Authorized moderators/admins may moderate posts and reports.
- Frontend button visibility is never an authorization mechanism.


2. TABLES CREATED
----------------------------------------------------------------------

Existing tables:

- users
- profiles

Social tables:

- posts
- connections
- follows
- post_likes
- saved_posts
- comments
- post_reports

Main relationships:

users 1 -> many posts
users 1 -> many comments
users 1 -> many post_likes
users 1 -> many saved_posts
users 1 -> many post_reports
users many -> many users through connections
users many -> many users through follows
posts 1 -> many comments
posts 1 -> many post_likes
posts 1 -> many saved_posts
posts 1 -> many post_reports


3. TABLE RESPONSIBILITIES
----------------------------------------------------------------------

posts

- Internal primary key: BIGINT UNSIGNED id
- Public identifier: BINARY(16) public_id
- Author reference: user_id -> users.id
- Post text: content
- Optional Cloudinary image reference: image_public_id
- created_at and updated_at timestamps
- deleted_at for soft deletion
- public_id is unique
- A post must contain text, an image, or both

The public_id is used at the URL/API boundary. Related tables should
reference the internal posts.id for efficient joins.

connections

- Stores connection requests and accepted connections
- Stores users as user_low_id and user_high_id
- Stores requested_by and status
- Status values: pending, accepted, rejected
- A unique user pair prevents A -> B and B -> A being separate rows
- user_low_id must be lower than user_high_id

follows

- Stores follower_user_id and followed_user_id
- Unique pair prevents duplicate follows
- A user cannot follow themselves
- Following is independent from connecting

post_likes

- Stores post_id and user_id
- Composite primary key prevents duplicate likes
- Removing a like deletes the relationship row

saved_posts

- Stores post_id and user_id
- Composite primary key prevents duplicate saves
- Removing a save deletes the relationship row

comments

- Stores post_id, user_id, and content
- Stores created_at, updated_at, and deleted_at
- First version supports normal comments only, not nested replies
- Comment authors may edit/delete their own comments
- Moderators may remove comments

post_reports

- Stores post_id and reporter_user_id
- Stores reason, optional description, and status
- Status values: pending, reviewed, dismissed, action_taken
- Unique post/reporter pair prevents duplicate reports
- reviewed_by and reviewed_at are set by moderation actions
- The reviewer-fields rule is enforced by backend logic because MySQL
	does not allow that CHECK constraint with the reviewer foreign key's
	ON DELETE SET NULL action


4. IDENTIFIER DECISION
----------------------------------------------------------------------

The project uses ramsey/uuid 4.9.4, installed through Composer.

composer.json and composer.lock were updated, and vendor/autoload.php
was regenerated.

Generate a public post ID with:

use Ramsey\\Uuid\\Uuid;

$publicId = Uuid::uuid7()->getBytes();

UUIDv7 is time-ordered and stored in 16 bytes in the BINARY(16) column.
It makes simple ID enumeration difficult, but it is not authorization.
Every backend operation must still authenticate the user and verify
visibility, ownership, or permission.


5. DATABASE VERIFICATION
----------------------------------------------------------------------

Run these queries in MySQL:

SHOW TABLES;

DESCRIBE posts;
DESCRIBE connections;
DESCRIBE follows;
DESCRIBE post_likes;
DESCRIBE saved_posts;
DESCRIBE comments;
DESCRIBE post_reports;

Verify the foreign keys:

SELECT
		TABLE_NAME,
		CONSTRAINT_NAME,
		COLUMN_NAME,
		REFERENCED_TABLE_NAME,
		REFERENCED_COLUMN_NAME
FROM information_schema.KEY_COLUMN_USAGE
WHERE TABLE_SCHEMA = DATABASE()
	AND TABLE_NAME IN (
			'posts',
			'connections',
			'follows',
			'post_likes',
			'saved_posts',
			'comments',
			'post_reports'
	)
	AND REFERENCED_TABLE_NAME IS NOT NULL
ORDER BY TABLE_NAME, CONSTRAINT_NAME;

Verify the UUID column specifically:

SHOW COLUMNS FROM posts LIKE 'public_id';

Expected type: binary(16).


6. SECURITY RULES
----------------------------------------------------------------------

Backend:

- Require login for post and social actions.
- Use prepared PDO statements for all user input.
- Use the authenticated session user ID, never a submitted author ID.
- Check post ownership in UPDATE and DELETE conditions.
- Check comment ownership before editing/deleting comments.
- Check moderator permission before changing reports.
- Validate that a connection requester is one of the two users.
- Validate upload MIME type, size, dimensions, and file contents.
- Store Cloudinary references, not uploaded binary data in MySQL.
- Use CSRF protection on every state-changing POST request.
- Validate and escape output when rendering HTML.

Database:

- Foreign keys protect references.
- Unique keys prevent duplicate likes, saves, follows, connections,
	and reports.
- CHECK constraints validate statuses and non-empty text where used.
- ON DELETE CASCADE removes dependent interaction records when a user
	or post is permanently deleted.

Frontend:

- Display Connect, Pending, or the overflow menu based on backend state.
- Display Follow/Unfollow based on the separate follows state.
- Display Save/Unsave based on the saved_posts state.
- Never rely on hidden buttons for security.

9. TEST CHECKLIST
----------------------------------------------------------------------

Database:

- Foreign keys reject nonexistent users and posts.
- Duplicate likes are rejected.
- Duplicate saves are rejected.
- Duplicate follows are rejected.
- Reverse duplicate connections are rejected.
- Duplicate reports are rejected.
- Self-follow and self-connection are rejected.

Authorization:

- Unauthenticated users cannot create or modify posts.
- Users cannot edit another user's post.
- Users cannot delete another user's post.
- Users cannot edit another user's comment.
- Users cannot review reports without moderator permission.
- Random or guessed public IDs do not bypass authorization.

Features:

- Create text-only post.
- Create image-only post if supported by the posts CHECK constraint.
- Create text and image post.
- Edit owned post.
- Soft-delete owned post.
- Like and unlike.
- Save and unsave.
- Create, edit, and delete comments.
- Connect, show Pending, accept, and reject.
- Follow and unfollow independently from connections.
- Report a post.
- Review, dismiss, or take action on a report.
- Share a public post URL without creating a share table.
