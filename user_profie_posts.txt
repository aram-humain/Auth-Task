Task 4: User Profile Management + Posts

Goal

Continue the existing Authentication and Role Management system by adding User Profile and Posts functionality.

A user should be able to have a personal profile, update their information, have a profile picture, and publish posts.

This functionality should work with the existing authentication and authorization system.


--------------------------------------------------

--------------------------------------------------

Each registered user should have a profile.

The profile should contain at least:

- First Name
- Last Name
- Phone
- Location
- Date of Birth
- Bio
- Profile Picture

The user should be able to view and update their profile information.


--------------------------------------------------
2. Profile Picture
--------------------------------------------------

The user should be able to:

- Add a profile picture
- Replace an existing profile picture
- Remove a profile picture

The profile should also work correctly when the user does not have a profile picture.


--------------------------------------------------
3. Profile Access
--------------------------------------------------

Users should be able to view other users' profiles.

A user should only be able to modify their own profile.

An Admin should be able to view all user profiles.


--------------------------------------------------
4. Create Post
--------------------------------------------------

A logged-in user should be able to create a post.

A post should contain at least:

- Title
- Content
- Created Date

The post should be associated with the user who created it.


--------------------------------------------------
5. View Posts
--------------------------------------------------

Users should be able to view their own posts and posts created by other users.

A user's profile page should display the posts published by that user.

For example:

User A Profile
→ User A Posts

User B Profile
→ User B Posts


--------------------------------------------------
6. Edit Post
--------------------------------------------------

A user should be able to edit posts they created.

After an update, the new post information should be displayed wherever the post is shown.


--------------------------------------------------
7. Delete Post
--------------------------------------------------

A user should be able to delete posts they created.

A deleted post should no longer be available during normal application usage.


--------------------------------------------------
8. Post Ownership
--------------------------------------------------

A user should not be able to edit or delete another user's post.

Posts created by other users should only be available for viewing.


--------------------------------------------------
9. Posts Feed
--------------------------------------------------

Create a common page where users can view posts published in the system.

For example:

/posts.php

For each post, display at least:

- Author
- Title
- Content
- Created Date

It should be possible to navigate from the author's name to their profile page.


--------------------------------------------------
Expected User Flow

Register

→ View Other User Posts




Task 5: Comments, Likes, Categories and Content Moderation
Goal
Continue the existing system by turning the simple Posts functionality into a real
content platform with interaction and moderation.
The existing functionality:
Register
→ Email Verification
→ Login
→ Dashboard
→ Logout
→ Forgot / Reset Password
→ Roles and Permissions
→ Profile
→ Posts
must continue to work correctly.
The main goal of this task is to understand:
- How to model relations between several tables (one-to-many, many-to-many, self-referencing)
- How to protect write operations (CSRF, ownership checks, rate limiting)
- How to build listing pages that stay fast when there is a lot of data
- How moderation works on top of the existing Role and Permission system
- Why some data should be soft deleted instead of removed from the database
--------------------------------------------------
1. Post Status (Draft / Published / Archived)
--------------------------------------------------
A post should now have a status.
Possible values:
- draft
- published
- archived
Rules:
- A draft is visible only to its author (and to Admin).
- A published post is visible in the feed and on the author profile.
- An archived post is not shown in the feed, but the author can still see it.
- The author should be able to move a post between statuses.
- A new post can be saved either as a draft or published immediately.
The status value must be validated on the backend.
An unknown status must be rejected.
--------------------------------------------------
2. Categories and Tags
--------------------------------------------------
Add two different kinds of classification, because they use two different relations.
Category
- A post belongs to exactly one category.
- Example categories: News, Tutorial, Question, Other.
- Categories are stored in a separate table.
- Only an Admin can create, rename or delete a category.
Tags
- A post can have many tags, and a tag can belong to many posts.
- This requires a pivot table, for example: post_tag (post_id, tag_id).
- A user enters tags as free text, for example: php, mysql, security
- If a tag already exists, reuse it instead of creating a duplicate.
- Tag names should be normalized (lowercase, trimmed).
Requirements:
- Deleting a category that still has posts must not break those posts.
  Decide and explain your approach (block the delete, or move posts to a default category).
- The feed should be filterable by category and by tag.
--------------------------------------------------
3. Post Images
--------------------------------------------------
A post should be able to have images.
Requirements:
- A post can have several images (one-to-many relation).
- Validate the file type (only images).
- Validate the file size (set a maximum, for example 2 MB).
- Do not trust the original file name — generate your own name on the server.
- Store the files outside of the database; store only the path in the database.
- Deleting a post should also handle its images.
- The post must display correctly when it has no images.
Important:
- Do not trust the extension sent by the browser.
- Do not trust the MIME type sent by the browser.
- Check the real file type on the server.
--------------------------------------------------
4. Comments
--------------------------------------------------
A logged-in and verified user should be able to comment on a published post.
A comment should contain at least:
- Post ID
- User ID
- Content
- Created date
Rules:
- Only logged-in and verified users can create comments.
- Comments cannot be added to a draft or archived post.
- The author of a comment can edit and delete their own comment.
- The author of the post can delete any comment on their own post.
- A Moderator or Admin can delete any comment.
- A regular user must not be able to edit or delete someone else's comment.
Display the number of comments next to each post in the feed.
--------------------------------------------------
5. Nested Replies
--------------------------------------------------
A comment should be able to be a reply to another comment.
This is a self-referencing relation, for example:
comments
- id
- post_id
- user_id
- parent_id  (nullable)
- content
- created_at
Requirements:
- Show replies under their parent comment.
- Limit the nesting to 2 levels (comment → reply). A reply to a reply attaches
  to the same parent.
- A reply must belong to the same post as its parent comment.
  Sending a parent_id from a different post must be rejected.
- Deleting a parent comment must handle its replies correctly.
  Decide and explain your approach.
--------------------------------------------------
6. Likes
--------------------------------------------------
A user should be able to like and unlike a post.
Requirements:
- One user can like the same post only once.
- Clicking again removes the like (toggle).
- Show the total number of likes for each post.
- Show whether the current user already liked the post.
- A user cannot like a draft or archived post.
Database:
- Use a pivot table, for example: post_likes (user_id, post_id, created_at)
- Add a UNIQUE constraint on (user_id, post_id).
Do not rely only on PHP code to prevent duplicates.
The database must also protect this rule.
--------------------------------------------------
7. Soft Delete
--------------------------------------------------
Posts and comments should not be physically deleted from the database.
Add a field, for example:
deleted_at
Rules:
- A deleted post must not appear in the feed, on the profile, or on its own page.
- A deleted comment must not be shown.
- All queries must exclude soft deleted records.
- An Admin should be able to see deleted posts on a separate page and restore them.
Be careful:
Every existing query that reads posts or comments must be updated.
A single forgotten query will show deleted content.
--------------------------------------------------
8. Search, Filtering and Pagination
--------------------------------------------------
The feed page (/posts.php) should support:
Search
- Search by post title and content.
Filters
- By category
- By tag
- By author
Sorting
- Newest first
- Most liked
- Most commented
Pagination
- Show a fixed number of posts per page, for example 10.
- Show page numbers or Previous / Next.
- The current search, filter and sort values must be preserved when changing page.
Requirements:
- All filter values come from the URL (GET parameters).
- All values must be validated. An invalid page number, sort value or category ID
  must not break the page and must not reach the SQL query directly.
- Search and filters must be implemented with prepared statements.
  String concatenation into SQL is not allowed.
--------------------------------------------------
9. Performance (N+1 Problem)
--------------------------------------------------
The feed shows a list of posts with:
- Author name
- Category
- Tags
- Like count
- Comment count
The naive solution runs one query per post to get this information.
With 10 posts that becomes more than 30 queries.
Requirements:
- Do not run a query inside a loop.
- Load the related data with JOIN, GROUP BY or a small number of additional queries
  that fetch data for all posts at once (for example WHERE post_id IN (...)).
- Count the total number of SQL queries used to render the feed page and be ready
  to report the number.
Target: a feed page with 10 posts should not need more than about 5 queries.
--------------------------------------------------
10. CSRF Protection
--------------------------------------------------
All forms that change data must be protected against CSRF.
This includes:
- Create / edit / delete post
- Create / edit / delete comment
- Like / unlike
- Profile update
- Role change (from Task 3)
Requirements:
- Generate a CSRF token and store it in the session.
- Add the token as a hidden field in every POST form.
- Verify the token on the server before processing the request.
- If the token is missing or wrong, reject the request.
- Compare tokens safely (hash_equals), not with a simple ==.
Be ready to demonstrate:
Submitting a form without a valid token must fail.
--------------------------------------------------
11. Rate Limiting
--------------------------------------------------
Prevent spam and abuse on write actions.
Examples:
- Maximum 5 comments per minute per user
- Maximum 10 posts per day per user
- Maximum 5 failed login attempts in 15 minutes per email or IP
Requirements:
- Store the attempts in the database or in the session.
- When the limit is reached, show a clear message and reject the action.
- Explain where you store the counters and why.
Note: failed login attempts must be limited per email or IP,
not only in the current session, otherwise the limit is easy to bypass.
--------------------------------------------------
12. Moderation
--------------------------------------------------
Connect the content to the existing Role and Permission system.
Add new permissions, for example:
- create_post
- moderate_posts
- moderate_comments
- view_deleted_posts
Assign them:
User
- create_post
Moderator
- create_post
- moderate_posts
- moderate_comments
Admin
- everything above
- view_deleted_posts
Moderator page (/moderator.php) should allow:
- Viewing reported posts and comments
- Hiding (soft deleting) a post or comment
- Seeing who reported it and why
Report functionality:
- A logged-in user can report a post or a comment.
- A report contains: reporter, target, reason, created date.
- The same user cannot report the same item twice.
- The author cannot report their own content.
All moderation actions must be checked with the permission system,
using can('moderate_posts') style checks — not with if ($role === 'admin').
--------------------------------------------------
13. Activity Log
--------------------------------------------------
Record important actions in a separate table.
For example:
activity_log
- id
- user_id
- action
- target_type
- target_id
- ip_address
- created_at
Log at least:
- Post created / updated / deleted
- Comment deleted by a moderator
- Role changed
- Failed login attempt
- Password reset
An Admin should be able to view the log with pagination and a filter by user.
--------------------------------------------------
14. Transactions
--------------------------------------------------
Some operations touch more than one table.
For example, creating a post with tags and images:
1. Insert the post
2. Insert or find the tags
3. Insert the rows in post_tag
4. Insert the image rows
If one of these steps fails, the database must not be left in a broken state
(for example a post with no tags, or tags pointing to a post that was not created).
Requirements:
- Use a transaction (beginTransaction, commit, rollBack).
- On error, roll back and show the user a clear message.
- Be ready to demonstrate a rollback by forcing an error in the middle.
--------------------------------------------------

--------------------------------------------------
Scenario 1
User A opens the edit page of User B's post.
→ Access denied
Scenario 2
User A sends a POST request to delete User B's post,
with User B's post ID in the request body.
→ Request rejected
Scenario 3

→ Request rejected
Scenario 4
A non-verified user tries to create a post or a comment.
→ Request rejected
Scenario 5
A guest (not logged in) opens the feed.
→ Posts are visible, but Like, Comment and Report are not available.

Scenario 6
A Moderator deletes a comment on someone else's post.
→ Allowed, and the action appears in the activity log.
Scenario 7
A regular user opens the deleted posts page.
→ Access denied
Scenario 8
A user opens:
/posts.php?page=-5&sort=; DROP TABLE users; --
→ The page must work normally and must not execute anything dangerous.

The project is now bigger, so structure matters.
Suggested separation:

Rules:
- SQL, HTML and business logic must not be mixed in the same file.
- Validation logic should be reusable, not copy-pasted on every page.
- Repeated HTML (header, footer, post card, comment block) should be in shared files.
- No SQL query inside a loop.
--------------------------------------------------
17. Database Requirements
--------------------------------------------------

- Add a UNIQUE constraint where a rule requires uniqueness

- Add indexes on the columns used for filtering and sorting
  (post_id, user_id, created_at, status, deleted_at).

POSTS / SOCIAL NETWORK IMPLEMENTATION HANDOFF

This section records the database design agreed for the pilot social
network and the work that remains. No application code has been
implemented for these social features yet.


1. AGREED ARCHITECTURE
----------------------------------------------------------------------

The application uses:

- PHP
- PDO
- MySQL 8.0
- InnoDB
- Session authentication through includes/auth.php
- Cloudinary for uploaded images
- The existing Dashboard as the feed page

There will not be a separate Feed component for now. Dashboard.php will
load the feed data and Dashboard.html.php will render it.

Visibility decision:

- Authenticated users may view posts.
- Only the post owner may edit or delete their post.
- Authorized moderators/admins may moderate posts and reports.
- Frontend button visibility is never an authorization mechanism.


2. TABLES CREATED
----------------------------------------------------------------------

Existing tables:

- users
- profiles

Social tables:

- posts
- connections
- follows
- post_likes
- saved_posts
- comments
- post_reports

Main relationships:

users 1 -> many posts
users 1 -> many comments
users 1 -> many post_likes
users 1 -> many saved_posts
users 1 -> many post_reports
users many -> many users through connections
users many -> many users through follows
posts 1 -> many comments
posts 1 -> many post_likes
posts 1 -> many saved_posts
posts 1 -> many post_reports


3. TABLE RESPONSIBILITIES
----------------------------------------------------------------------

posts

- Internal primary key: BIGINT UNSIGNED id
- Public identifier: BINARY(16) public_id
- Author reference: user_id -> users.id
- Post text: content
- Optional Cloudinary image reference: image_public_id
- created_at and updated_at timestamps
- deleted_at for soft deletion
- public_id is unique
- A post must contain text, an image, or both

The public_id is used at the URL/API boundary. Related tables should
reference the internal posts.id for efficient joins.

connections

- Stores connection requests and accepted connections
- Stores users as user_low_id and user_high_id
- Stores requested_by and status
- Status values: pending, accepted, rejected
- A unique user pair prevents A -> B and B -> A being separate rows
- user_low_id must be lower than user_high_id

follows

- Stores follower_user_id and followed_user_id
- Unique pair prevents duplicate follows
- A user cannot follow themselves
- Following is independent from connecting

post_likes

- Stores post_id and user_id
- Composite primary key prevents duplicate likes
- Removing a like deletes the relationship row

saved_posts

- Stores post_id and user_id
- Composite primary key prevents duplicate saves
- Removing a save deletes the relationship row

comments

- Stores post_id, user_id, and content
- Stores created_at, updated_at, and deleted_at
- First version supports normal comments only, not nested replies
- Comment authors may edit/delete their own comments
- Moderators may remove comments

post_reports

- Stores post_id and reporter_user_id
- Stores reason, optional description, and status
- Status values: pending, reviewed, dismissed, action_taken
- Unique post/reporter pair prevents duplicate reports
- reviewed_by and reviewed_at are set by moderation actions
- The reviewer-fields rule is enforced by backend logic because MySQL
	does not allow that CHECK constraint with the reviewer foreign key's
	ON DELETE SET NULL action


4. IDENTIFIER DECISION
----------------------------------------------------------------------

The project uses ramsey/uuid 4.9.4, installed through Composer.

composer.json and composer.lock were updated, and vendor/autoload.php
was regenerated.

Generate a public post ID with:

use Ramsey\\Uuid\\Uuid;

$publicId = Uuid::uuid7()->getBytes();

UUIDv7 is time-ordered and stored in 16 bytes in the BINARY(16) column.
It makes simple ID enumeration difficult, but it is not authorization.
Every backend operation must still authenticate the user and verify
visibility, ownership, or permission.


5. DATABASE VERIFICATION
----------------------------------------------------------------------

Run these queries in MySQL:

SHOW TABLES;

DESCRIBE posts;
DESCRIBE connections;
DESCRIBE follows;
DESCRIBE post_likes;
DESCRIBE saved_posts;
DESCRIBE comments;
DESCRIBE post_reports;

Verify the foreign keys:

SELECT
		TABLE_NAME,
		CONSTRAINT_NAME,
		COLUMN_NAME,
		REFERENCED_TABLE_NAME,
		REFERENCED_COLUMN_NAME
FROM information_schema.KEY_COLUMN_USAGE
WHERE TABLE_SCHEMA = DATABASE()
	AND TABLE_NAME IN (
			'posts',
			'connections',
			'follows',
			'post_likes',
			'saved_posts',
			'comments',
			'post_reports'
	)
	AND REFERENCED_TABLE_NAME IS NOT NULL
ORDER BY TABLE_NAME, CONSTRAINT_NAME;

Verify the UUID column specifically:

SHOW COLUMNS FROM posts LIKE 'public_id';

Expected type: binary(16).


6. SECURITY RULES
----------------------------------------------------------------------

Backend:

- Require login for post and social actions.
- Use prepared PDO statements for all user input.
- Use the authenticated session user ID, never a submitted author ID.
- Check post ownership in UPDATE and DELETE conditions.
- Check comment ownership before editing/deleting comments.
- Check moderator permission before changing reports.
- Validate that a connection requester is one of the two users.
- Validate upload MIME type, size, dimensions, and file contents.
- Store Cloudinary references, not uploaded binary data in MySQL.
- Use CSRF protection on every state-changing POST request.
- Validate and escape output when rendering HTML.

Database:

- Foreign keys protect references.
- Unique keys prevent duplicate likes, saves, follows, connections,
	and reports.
- CHECK constraints validate statuses and non-empty text where used.
- ON DELETE CASCADE removes dependent interaction records when a user
	or post is permanently deleted.

Frontend:

- Display Connect, Pending, or the overflow menu based on backend state.
- Display Follow/Unfollow based on the separate follows state.
- Display Save/Unsave based on the saved_posts state.
- Never rely on hidden buttons for security.
